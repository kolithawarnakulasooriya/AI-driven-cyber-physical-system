# Agents

This document outlines the autonomous agent architecture and workflow patterns used across the AI-driven cyber-physical system projects. It serves as a centralized reference for developers who need to understand, extend, or troubleshoot the agent ecosystem.

## Overview
Agents are self-contained computational units that encapsulate domain-specific logic, tool usage, and execution contexts. Each agent operates in an isolated environment with its own working directory, toolset, and memory scope. The architecture emphasizes modularity, reproducibility, and composability.

## Agent Types
- **Leaf Agents**: Basic execution units that perform a single task or a small set of related tasks. They cannot spawn sub-agents.
- **Orchestrator Agents**: Higher-level agents that can spawn and coordinate multiple leaf agents. Currently disabled by default due to nesting restrictions.

## Execution Model
Agents run in the background and communicate exclusively through the Hermes message bus. Results are returned as new messages when the agent completes. Background tasks can be scheduled via `cronjob` for recurring operations.

## Skills Integration
Skills are the primary mechanism for encapsulating reusable procedures. All agents load and invoke skills to perform domain-specific operations (e.g., `sensorhub-management`, `repo-code-management`). Skills are versioned and stored under `~/.hermes/skills/`.

## Development Workflow
1. Create or update a skill using `skill_manage`.
2. Reference the skill in the agent's task prompt.
3. Load the skill explicitly via `skill_load` if required.
4. Execute the agent and monitor its output.

## Verification
Agents must include a verification step in their procedure to confirm successful completion. Typical verification commands involve checking file outputs, API responses, or state changes.
